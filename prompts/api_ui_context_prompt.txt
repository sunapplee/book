Я передал контексты модулей A–C и задание на API и UI. На их основе собери проверенный технический контекст для реализации API и UI.

Главный принцип: полный поиск по проекту, выборочное чтение файлов и компактный отчёт только со сведениями, необходимыми для подключения данных и моделей. Анализировать файлы можно подробно; печатать нужно найденные ответы на конкретные вопросы.

1. Первый запуск: компактная диагностика

Изучи задание и контексты. Определи, какие файлы и сведения нужны для реализации API и UI. Дай готовый самостоятельный Python-код для их проверки.

Начинай с общего корня проекта, в котором находятся папки всех модулей. Задай его в PROJECT_ROOT. Если код запускается из модуля D или другой вложенной папки, найди общий корень по путям из контекстов и расположению модулей. Не принимай текущую рабочую директорию за корень автоматически. Все пути строй от PROJECT_ROOT.

Выполни рекурсивный поиск по всему PROJECT_ROOT, включая A–C. Пропускай .git, виртуальные окружения, site-packages, node_modules, кэши, .ipynb_checkpoints и .virtual_documents. Делай вывод об отсутствии файла после поиска по всему корню. В отчёт включай только нужные файлы, каждый путь один раз.

Используй файлы на диске и переданные контексты. Код должен работать в чистом ядре или отдельным скриптом. Не ищи объекты в памяти ноутбука и не используй globals(), locals() или состояние ядра.

Первый отчёт должен содержать:
— PROJECT_ROOT, папки модулей и пути к нужным данным, моделям и границам;
— для таблиц: нужные листы, полную схему столбцов и типов, поля дат и ключи связи; только необходимые короткие примеры;
— для моделей: результат загрузки, тип, шаги Pipeline, входные признаки в точном порядке, классы и необходимые категории преобразований;
— для геоданных: формат геометрии, CRS, если он установлен, и короткий пример без длинных координат;
— версии библиотек, влияющих на загрузку и работу моделей, и краткие сообщения об ошибках.

Способ загрузки модели выбирай по контексту или коду сохранения, а не только по расширению файла. Одинаковые схемы и списки признаков выводи один раз с указанием моделей или файлов, к которым они относятся.

Большие таблицы читай выборочно. Статистику по образцу обозначай как статистику образца. Не считай строки, пропуски и распределения по всему набору, если это не требуется для реализации. Примеры ограничь 1–3 короткими значениями только для полей, формат которых нужно уточнить.

Ограничь суммарный печатаемый вывод одного запуска 12 000 символами. Сначала собери сведения в структуру, затем сформируй единый отчёт и проверь его объём перед печатью. При превышении убирай повторы, необязательные примеры и дополнительные сведения. Если обязательные данные всё равно не помещаются, перенеси часть целых проверок на следующий шаг и кратко перечисли, что осталось. Не обрезай посередине схемы, списки признаков и сообщения об ошибках.

Не печатай полный список всех файлов, исходники целиком, массовые подборки ячеек и их сохранённые выводы, HTML, длинные геометрии, полный get_params(deep=True) и внутреннее содержимое моделей. Не выгружай повторно уже переданные контексты и задание из TXT, PDF или DOCX. Хэши, байты файлов, pickle-опкоды и подробные трассировки нужны только для разбора конкретной ошибки.

В первом ответе выдай инструкции и диагностический код. Дождись моего вывода. Если выполнение может занять более 10 секунд, предупреди об этом. Не выполняй ячейки найденных ноутбуков, не переобучай модели и не изменяй исходные данные.

2. Точечные уточнения

По полученному отчёту определи, каких сведений ещё не хватает. Дай дополнительный код только для этих вопросов, без повторной общей диагностики.

При необходимости читай .py и .ipynb как файлы, чтобы найти конкретную формулу признака, сигнатуру функции, правила обработки или команду сохранения. Выводи только нужную формулу, сигнатуру или небольшой фрагмент функции с путём и номером ячейки. Не печатай все совпадения поиска.

Когда известны загрузка, входная схема и подготовка признаков, при необходимости добавь один пример полного прохода от данных до предсказания. Выведи краткий вход и результат. Соблюдай тот же общий бюджет вывода и дождись моих результатов.

3. Итоговый контекст для API и UI

Собери единый технический текст для следующего агента:
— требуемые функции API и UI по заданию;
— PROJECT_ROOT, подтверждённые пути файлов, способы чтения и ключи связи;
— загрузка моделей, состав Pipeline, порядок признаков, классы и категории;
— формулы вычисляемых признаков, единицы и последовательность обработки;
— используемые функции, их расположение, сигнатуры и зависимости;
— форматы входов и результатов, необходимые примеры и версии библиотек;
— краткий список сведений или файлов, которых ещё не хватает.

Не повторяй историю обучения, сравнения метрик и хронологию диагностики, если они не влияют на реализацию. Разделяй подтверждённые факты и предлагаемые решения. Найденную команду сохранения отличай от фактического наличия файла. Не придумывай пути, функции, формулы и результаты проверок.

Пиши по-русски, кратко и конкретно. Сохраняй необходимые технические детали. Код самого API и UI пока не составляй.
