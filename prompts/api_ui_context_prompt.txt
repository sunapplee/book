Я передал контексты модулей A–C и задание на API и UI. На их основе собери проверенный технический контекст для реализации API и UI.

Порядок работы: сохранённые артефакты → конкретные недостающие сведения → итоговый контекст. Исследуй файлы подробно, если нужно, но печатай только ответы, от которых зависит реализация. Типы данных, проверки и библиотеки выбирай по заданию и фактическим артефактам.

Общие правила

Начинай с общего PROJECT_ROOT, где находятся папки всех модулей. Если код запускается из модуля D или вложенной папки, определи общий корень по контекстам и расположению модулей. Все пути строй от него. Ищи рекурсивно по всему корню, включая A–C; об отсутствии файла суди после полного поиска.

Пропускай .git, виртуальные окружения, site-packages, node_modules, кэши, .ipynb_checkpoints и .virtual_documents. Исключай созданные в ходе этой проверки диагностические скрипты, блоки ноутбуков, их копии и сохранённые выводы: они не являются исходной логикой проекта. Не исключай рабочий файл только из-за его имени.

Работай с файлами на диске и переданными контекстами. Дай самостоятельный Python-код для чистого ядра или отдельного скрипта. Не ищи объекты в памяти ноутбука, не используй globals() и locals(), не выполняй найденные ноутбуки, не переобучай модели и не изменяй исходные данные. Если выполнение может занять больше 10 секунд, предупреди об этом.

1. Сначала артефакты — вывод до 4000 символов

Изучи задание, выбери необходимые сохранённые данные, модели, преобразования и настройки. Первый ответ — короткая инструкция и код их проверки. Дождись моего вывода.

Первый отчёт:
— PROJECT_ROOT и пути только к нужным артефактам, каждый один раз;
— формат и необходимая структура данных; схемы, размерности, ключи и параметры чтения — по применимости;
— результат загрузки моделей и преобразований, библиотека, тип, необходимые входы и выходы, сохранённая обработка;
— только значимые для чтения и загрузки версии библиотек и краткие ошибки.

Начинай с содержимого сохранённых артефактов. Способ загрузки выбирай по контексту, настройкам или команде сохранения. Если он неизвестен, извлеки из исходников только ответ о способе сохранения и загрузки. Не откладывай разбор артефактов ради изучения всей истории обучения. Версии установленных дистрибутивов можно получить через importlib.metadata.

Общие схемы и входы нескольких моделей показывай один раз. Большие данные читай выборочно, полную статистику не считай без необходимости. Примеры значений добавляй только для уточнения формата, большие объекты не печатай. Задание, чек-лист требований и план будущего API в диагностический вывод не включай.

2. Затем конкретные пробелы — вывод до 2000 символов за шаг

Используй уже подтверждённые сведения. На каждом шаге сформулируй не более трёх конкретных вопросов и кратко укажи, для какого действия в API или UI нужен каждый ответ. Дай код только для этих вопросов и дождись моих результатов. Не повторяй общую инвентаризацию и полученные ответы.

Исходники и .ipynb читай как файлы во всех нужных модулях. Извлекай конкретный факт: способ загрузки, точную формулу с параметрами, сигнатуру или правило обработки. В отчёт передавай ответ и его источник — путь и строку или номер ячейки. Не печатай ячейки целиком, подборки совпадений по регулярным выражениям, код обучения, подбора моделей или метрик. Небольшую функцию подготовки можно привести целиком, только если именно её реализация нужна для переноса в API и она отвечает заданному вопросу.

Для каждого нужного вида входа установи источник, формат, обязательность, допустимые значения и обработку пропусков. Разделяй пользовательский ввод, данные из файлов и вычисляемые значения. Подготовку и преобразования фиксируй точно, с параметрами.

Когда входы и обработка известны, дай минимальный пример для каждой используемой модели или самостоятельной цепочки: реальные данные → подготовка → вызов → результат. Общую подготовку используй повторно. Выведи только способ выбора примера, необходимые параметры и краткий результат. Проверь соответствие типов, структуры и содержимого результата; ошибку не считай успехом. Если запуск невозможен, укажи конкретную причину и статус проверки.

Отделяй пробелы в сведениях о существующих артефактах от функций, которые предстоит разработать в модуле D. Будущие API-обработчики и элементы UI отмечай как задачи разработки; не ищи подтверждение их наличия и не задерживай из-за этого сбор контекста.

Правила объёма диагностического вывода

В каждый блок кода встрой общий лимит печати: первый запуск — 4000 символов, каждый последующий — 2000. Лимит относится ко всему отчёту, включая заголовки и сообщения. Сначала собери ответы, затем сформируй одну строку, проверь её длину и напечатай один раз. Не печатай промежуточные результаты внутри обхода файлов или ячеек.

Лимит — верхняя граница, заполнять его не нужно. Убирай повторы и необязательные сведения. Не обрезай ответ, формулу или список посередине; при необходимости перенеси целый конкретный вопрос на следующий шаг. Не выводи исходники целиком, сохранённые выводы ноутбуков, HTML, полные наборы параметров, веса и внутренние дампы моделей, длинные трассировки или повторно переданные тексты задания и контекстов.

3. Итоговый контекст для API и UI

Когда необходимые сведения получены либо оставшиеся пробелы точно определены, собери единый технический текст. Таблицу требований включай только сюда:
— каждый пункт и подпункт API/UI с исходным номером → нужные данные и обработка → что доступно → что разработать или уточнить;
— PROJECT_ROOT, подтверждённые пути, способы чтения и загрузки артефактов;
— точные входы, выходы и преобразования, источники значений, обязательность и обработка пропусков;
— необходимые функции и формулы, их параметры, расположение и зависимости;
— минимальные примеры, фактические результаты или статус проверки и значимые версии библиотек;
— конкретные недостающие сведения или файлы и действия для их получения.

Сверь контекст со всеми пунктами задания. Разделяй подтверждённое состояние и будущую разработку. Не придумывай пути, формулы, файлы и результаты. Историю обучения, метрики и хронологию диагностики включай только при влиянии на реализацию. Лимиты 4000/2000 относятся к выводу диагностического кода; итоговый контекст должен сохранять необходимые технические сведения без повторов.

Пиши по-русски, кратко и конкретно. Код самого API и UI пока не составляй.
