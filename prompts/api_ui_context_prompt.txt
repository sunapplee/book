Я передал контексты модулей A–C и задание на API и UI. На их основе собери проверенный технический контекст для реализации API и UI.

Главный принцип: полный поиск по проекту, выборочное чтение файлов и компактный отчёт только со сведениями, необходимыми для подключения данных и моделей. Анализировать файлы можно подробно; печатать нужно найденные ответы на конкретные вопросы.

1. Первый запуск: компактная диагностика

Изучи задание и контексты. Определи, какие файлы и сведения нужны для реализации API и UI. Дай готовый самостоятельный Python-код для их проверки.

Сопоставь каждый пункт и подпункт задания на API и UI с необходимыми данными, артефактами и обработкой. Сохраняй исходную нумерацию. Учитывай требования, для которых готовых функций в контексте ещё нет.

Начинай с общего корня проекта, в котором находятся папки всех модулей. Задай его в PROJECT_ROOT. Если код запускается из модуля D или другой вложенной папки, найди общий корень по путям из контекстов и расположению модулей. Не принимай текущую рабочую директорию за корень автоматически. Все пути строй от PROJECT_ROOT.

Выполни рекурсивный поиск по всему PROJECT_ROOT, включая A–C. Пропускай .git, виртуальные окружения, site-packages, node_modules, кэши, .ipynb_checkpoints и .virtual_documents. Делай вывод об отсутствии файла после поиска по всему корню. В отчёт включай только нужные файлы, каждый путь один раз.

Используй файлы на диске и переданные контексты. Код должен работать в чистом ядре или отдельным скриптом. Не ищи объекты в памяти ноутбука и не используй globals(), locals() или состояние ядра.

Первый отчёт должен содержать:
— PROJECT_ROOT, папки модулей и пути к нужным данным, моделям и другим артефактам;
— для данных: формат, структуру, размерность и необходимые параметры чтения; схему столбцов, идентификаторы и ключи связи — если они применимы; только необходимые короткие примеры;
— для моделей: результат загрузки, библиотеку и тип модели, требуемые форматы и структуру входов и выходов, предобработку и постобработку; порядок признаков, классы и категории — если они применимы;
— версии библиотек, влияющих на загрузку и работу моделей, и краткие сообщения об ошибках.

Выбирай проверки по заданию, фактическим типам данных и используемым библиотекам. Способ загрузки модели выбирай по контексту или коду сохранения, а не только по расширению файла. Одинаковые описания входов, схемы и параметры выводи один раз с указанием моделей или файлов, к которым они относятся.

Для каждого необходимого вида входа установи источник данных, формат и структуру, обязательные элементы, допустимые значения и правила обработки пропусков. Разделяй данные, поступающие от пользователя, загружаемые из файлов и вычисляемые при обработке. Зафиксируй точную последовательность преобразований и их параметры, включая формулы, если они используются.

Большие данные читай выборочно. Статистику по образцу обозначай как статистику образца. Не вычисляй полную статистику по всему набору, если это не требуется для реализации. Показывай 1–3 коротких примера только там, где нужно уточнить формат.

Ограничь суммарный печатаемый вывод одного запуска 12 000 символами. Сначала собери сведения в структуру, затем сформируй единый отчёт и проверь его объём перед печатью. При превышении убирай повторы, необязательные примеры и дополнительные сведения. Если обязательные данные всё равно не помещаются, перенеси часть целых проверок на следующий шаг и кратко перечисли, что осталось. Не обрезай посередине схемы, списки признаков и сообщения об ошибках.

Не печатай полный список всех файлов, исходники целиком, массовые подборки ячеек и их сохранённые выводы, HTML, большие исходные объекты, полные наборы параметров и внутреннее содержимое моделей. Не выгружай повторно уже переданные контексты и задание из TXT, PDF или DOCX. Хэши, байты файлов, pickle-опкоды и подробные трассировки нужны только для разбора конкретной ошибки.

В первом ответе выдай инструкции и диагностический код. Дождись моего вывода. Если выполнение может занять более 10 секунд, предупреди об этом. Не выполняй ячейки найденных ноутбуков, не переобучай модели и не изменяй исходные данные.

2. Точечные уточнения

По полученному отчёту определи, каких сведений ещё не хватает. Дай дополнительный код только для этих вопросов, без повторной общей диагностики.

Ищи недостающие определения и преобразования в исходниках и ноутбуках всех модулей. Читай .py и .ipynb как файлы, чтобы найти конкретную формулу, сигнатуру функции, параметры обработки или команду сохранения. Выводи точную формулу с параметрами или нужный фрагмент кода с путём и номером строки или ячейки. Небольшую функцию, необходимую для переноса обработки, приводи целиком. Не печатай все совпадения поиска и не заменяй точную реализацию общим описанием метода.

Для каждой используемой модели или самостоятельной цепочки обработки дай диагностический код одного минимального примера: реальные входные данные → точная подготовка → вызов → результат. Выбирай данные, соответствующие обязательным значениям, типам и правилам обработки пропусков. В отчёте достаточно пути к примеру или кода его выбора, необходимых параметров и краткого результата; большие входные объекты не печатай. Соблюдай общий бюджет вывода и дождись моих результатов.

Считай пример проверенным по фактическому результату выполнения: проверь требуемые тип, структуру и содержимое результата и отсутствие необработанных ошибок. Если пример выполнить не удалось, укажи конкретную причину и что осталось проверить.
