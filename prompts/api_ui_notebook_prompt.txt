При этом каждый демонстрационный пример должен использовать корректный вход и проверять фактический результат своего вызова. Подтверждение работоспособности API не заменяет результат конкретного примера.

Для каждого пункта соблюдай структуру:

— Одна начальная Markdown-ячейка: исходный номер и название пункта, краткое описание задачи, выбранный подход и почему он подходит.
— Одна или несколько кодовых ячеек Python для демонстрации соответствующего результата готового приложения. Разные этапы разделяй на ячейки, функцию сохраняй целиком. Для UI укажи конкретные действия пользователя, ожидаемое отображение и место для фактического скриншота, если он нужен.
— Одна итоговая Markdown-ячейка с кратким выводом по всему пункту: какая функция реализована, что она делает и чем подтверждается выполнение пункта. Успешность конкретной демонстрации подтверждай только её фактическим результатом.

Сохраняй номера и названия ровно как в задании. Разделение кода на ячейки не создаёт новых пунктов или подпунктов. Между кодовыми ячейками одного пункта не добавляй Markdown-шапки, повторные описания или промежуточные выводы. Новая шапка нужна только для следующего пункта задания.

Учитывай импорты и зависимости предыдущих ячеек. Указывай, к какому файлу приложения относится код.

Для успешных примеров используй реальные данные или файлы из проекта либо полученные через API. Проверяй формат, типы, обязательные значения и допустимость пропусков. Наличия поля недостаточно, если его значение недопустимо по контракту. Выбирай подходящий пример по этим условиям; не бери первую запись автоматически и не заполняй пропуски выдуманными значениями. Повторные примеры могут использовать общую подготовку, но каждый должен показать результат своего пункта.

HTTP-помощники должны проверять ожидаемый статус ответа и вызывать raise_for_status() для неожиданных HTTP-ошибок. Не возвращай JSON с ошибкой как успешный результат. После проверки статуса проверяй требуемые формат, структуру и содержимое ответа по контракту метода. Учитывай, что ответом может быть JSON, текст, файл или другой предусмотренный формат. HTTP 200 сам по себе не подтверждает выполнение функции.

Предусмотренные заданием ошибочные запросы показывай отдельно: проверяй ожидаемый статус и сообщение. Такая демонстрация подтверждает обработку ошибки, но не заменяет успешный пример основной функции.

Показывай результат, который требуется в пункте: вычисленные значения, присвоенную категорию, визуализацию, сформированный файл или другое предусмотренное действие. Список маршрутов, ответ о доступности сервиса или число полученных объектов не заменяют демонстрацию этого результата. Выводи результаты компактно, сохраняя сведения, необходимые для проверки пункта. Для UI подтверждай пользовательское действие и видимый результат; место для скриншота не считай готовым скриншотом.

Результат выдай одним Python-скриптом на nbformat, который создаёт файл module_notebook.ipynb. Используй отдельные Markdown- и кодовые ячейки, сохраняя описанную структуру.

Включи в скрипт полное содержимое всех ячеек, без сокращений, заглушек и необходимости вручную дописывать текст или код. Корректно экранируй кавычки и переносы строк.

Продолжай оформление ноутбука без запроса повторного подтверждения работоспособности API.

Если в предоставленных результатах есть ошибка, не описывай пример как успешный. Исправь вход или код демонстрации, когда причина установлена, и дай корректную ячейку. Если требуется изменение самого API или недостающий артефакт, точно укажи это для соответствующего пункта; не подменяй результат обещанием или заглушкой.
