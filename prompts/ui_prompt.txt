Базовой реализации достаточно, если пользователь получает предусмотренный заданием результат и это подтверждается простой проверкой. Интерфейс должен обращаться к API через его реальные методы с соблюдением форматов запросов и ответов. Серверную обработку данных и применение моделей выполняй через API. Для одного сценария можно вызывать несколько существующих методов API и объединять их ответы при формировании представления; отдельный endpoint для всей карточки или экрана не требуется.

Реализуй предусмотренные заданием ввод и загрузку данных, настройки, запуск операций, просмотр и скачивание результатов. Показывай состояние выполнения, обрабатывай ошибки ввода, недоступность API и пустые результаты понятными сообщениями. Отсутствие значения у отдельного объекта или ошибка одной независимой операции не должны блокировать остальные доступные результаты. Отсутствующие значения обозначай явно, не подменяя нулём или отрицательным результатом.

Закрывай составные требования полностью. Если пункт требует визуализации, фильтрации, выбора объектов, просмотра подробностей или другого взаимодействия, реализуй само действие и изменение отображаемого результата. Используй понятные названия элементов и подписи. Единицы измерения, легенды и другие пояснения добавляй там, где они нужны для интерпретации результата. Не используй заглушки, декоративные элементы вместо работающих функций и заранее прописанные ответы.

Перед выводом о нехватке данных проверь, можно ли получить требуемый результат с помощью имеющихся идентификаторов, связей и объектов. Не вводи дополнительные условия и требования к данным, если они не нужны для выполнения критерия. Если для обязательного сценария отсутствует метод API, реализуй минимально необходимое расширение API отдельным файлом или патчем с сохранением совместимости существующих методов. Не придумывай несуществующие маршруты и не переноси серверную обработку в UI. Если действительно не хватает данных или артефактов, точно укажи, на какую часть конкретного пункта это влияет, и реализуй остальные доступные требования.

Вынеси адрес API и основные настраиваемые параметры интерфейса в конфигурацию. Используй существующие настройки проекта или отдельный файл, сохраняя настройки API.

Предоставь структуру проекта, полный код файлов, зависимости и команды запуска. Если потребовалось расширение API, включи его код и порядок подключения.

Для каждого критерия UI реализуй требуемое действие пользователя, выполни минимально достаточный сценарий проверки и покажи фактический результат в интерфейсе. Обычно достаточно одного успешного сценария; если критерий требует несколько объектов, режимов или результатов, охвати их все. В рамках этой проверки убедись, что элементы управления меняют соответствующий результат и работают совместно там, где это требуется заданием. Ошибочные входы проверяй, когда это предусмотрено заданием. Дополнительный анализ выполняй только по требованию задания. Для успешных примеров используй реальные данные или файлы либо явно обозначенные контрольные входы с известным ожидаемым поведением или результатом. Соблюдай формат и обязательные значения. Проверь весь путь: ввод → действие пользователя → запрос к API → получение и отображение результата; сохранение или скачивание — если требуется заданием. Ошибку API не представляй как успешный результат операции. Не придумывай результаты проверок и скриншоты.

Контрольные значения и тестовые файлы допустимы для проверки сценариев, в том числе при отсутствии подходящих наблюдений в проекте. Помечай такие примеры как контрольные. Результат должен получаться при фактической работе UI и вызове API; ожидаемый ответ используй только для сравнения. Контрольные входы не выдавай за реальные наблюдения, а такую проверку — за оценку качества на реальных данных.
